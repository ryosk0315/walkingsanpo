# さんぽカード（仮）仕様

引き継ぎ書（HANDOFF.md）の第1〜11節をそのまま保存したもの。作業の前提は `CLAUDE.md` を参照。同梱ファイル（付録A）は実ファイルとして配置する。

## 1. 何を作るか
散歩を楽しくする、自分専用のWebアプリ（PWA）。既存アプリ（StepLens、Derivé系など）は更新が止まる不安があるので自作する。デートでも使える。

中心の流れ:
行き先を決める → お題 → 1枚撮る → ツイストカード → 反対側を撮る → 一言 → 「往復きっぷ」風の画像が自動で出来る → 共有

## 2. 決定済みの事項
- **形態**: iPhone向けのPWA。App Store審査・有料アカウントは使わない。サーバー・アカウントなし。データは端末内だけ。
- **ツイスト**: 1枚目を撮った**直後**に引く。中心概念は「反転」。引き直しは1回だけ。種類: 反転／見立て／撮らない／視点／時間。
- **お題の設計ルール**: 反転する2つの極に「主観の判断」が入ること。例: 一番うるさい色／静かな色、新しそう／古そう、手入れされている／放置されている、一番「まち」らしい形／らしくない形。**大きい／小さいは不採用**（客観的で面白くない）。
- **一言**: 対になった2枚に、選んだ理由を一言添える。
- **アルバム**: 1回の散歩を1枚の画像に自動でまとめる（「往復きっぷ」風。往＝1枚目、復＝ツイスト側）。
- **共有**: アルバム画像をスマホ標準の共有画面（Web Share API）に渡す。Instagramへの直接投稿はWebアプリではできない。ストーリーズ候補に出すには、`files` のみを渡し `title: ''` にするのがよい、という記事があるが、**実機未確認**。使えない環境用に、ダウンロード保存も用意する。
- **行き先**: 名前で一意に決まる実在の場所だけを出す。カテゴリは固定しない（細かくも粗くも調整可）。初期は駅・路線／寺社／橋／坂／町／イベント。各カードに「最寄り」「いつ」「理由」を出す。
- **理由は3種を切り替え**: 暦／歴史／好き。
- **デザイン**: 「街にある看板・標識」をテンプレートにする。データの形は共通で、見た目のテンプレートだけ種類ごとに持つ。最初の実装は2枚だけ（駅名標、由緒書き）。ほかは後から足す。

## 3. やらないこと（却下・後回し）
- 却下: 色パレット抽出、秘密の目的地、帰り道の補助、物語型のお題、同じスマホを2人で使う機能、AIが実行時に理由文を作ること。
- 後回し: 「見せ合い」（相手の画像を取り込んで並べる機能）。**画面・遷移・ボタンから外す**。ふたりモード（合言葉で同じお題を出す）も、最初は作らない。
- 後回し: イベントの行き先（手作業の収集が最大の負担）。
- 位置情報の自動記録は作らない。PWAは画面を閉じるとバックグラウンドで位置を取れない。必要なら、完了時の1点だけ前面で取る程度に留める。

## 4. 画面と遷移
1. ホーム: 「行き先を決める」「お題だけ引く」「これまでのアルバム」。
2. 行き先: 種類の切り替え、カード1枚（名前、最寄り、いつ、理由3種の切り替え）。「引き直す」「ここにする」。
3. お題: お題カード1枚。「撮影する」「パス」。
4. ツイスト: 1枚目を撮った直後に引く。「受けて立つ」で2枚目を撮る。引き直し1回。
5. 一言: 対の2枚＋一言入力。「保存して次のお題へ」「ここで終えてアルバムにする」。
6. アルバム（往復きっぷ）: 画像として保存／共有。
- 画面の見た目の見本は `docs/DESIGN_REFERENCE.md`（既存のモック）。モックはDCという独自形式のHTMLなので、**そのまま流用せず、見た目の参考として読む**。

## 5. 行き先データ
共通のスキーマ（例）:
```json
{
  "id": "washi-jinja",
  "name": "鷲神社",
  "kana": "わしじんじゃ",
  "category": "寺社",
  "near": [{ "station": "入谷駅", "line": "東京メトロ日比谷線" }],
  "coords": { "lat": 0, "lng": 0 },
  "rules": [{ "type": "otori" }],
  "reasons": {
    "history": { "text": "", "source": { "title": "", "url": "", "fetchedAt": "", "revision": "" } },
    "likes": ["祭り"]
  },
  "verified": false
}
```
- **暦の理由は日付のルールで計算する**（Wikipediaは使わない）。
  - 縁日: 毎月 8日=薬師、18日=観音、21日=弘法大師、24日=地蔵、28日=不動。
  - 酉の市: 11月の酉の日。2026年は 11/7（一の酉）と 11/19（二の酉）、三の酉はなし。実装後に必ずこの2日と一致するか、テストで確認すること。
  - 日付はJST。端末の時刻に依存する。
- **歴史の理由は Wikipedia の導入文を要約せず短く抜粋**し、「出典：Wikipedia『記事名』」と取得日を必ず表示する（CC BY-SA）。伝承・縁起は断定せず「〜とされる」の形にする。
- **好きの理由**: あらかじめ用意した「好き」の一覧（例: 古本、祭り、坂、古い門前町）から、ユーザーが選ぶだけにする。場所ごとのタグ付けは `data/places.json` 側で事前に行う（AIが案を出し、Ryoが確認）。
- 検証済みでないデータ（`verified: false`）は、アプリに表示しない。
- イベントの情報は公式の情報源で確認する。Wikipediaには頼らない。

## 6. データ整備の手順（最初のスパイク）
`data/places.json`（30か所）と `scripts/fetch_wiki.mjs`、`.github/workflows/fetch-wiki.yml` が同梱されている。
1. リポジトリにこれらを置く。
2. Actionsの `fetch-wiki` を手動実行（Ryoがスマホから押す）。
3. `data/review.html` と `data/wiki_check.json` が保存される。
4. Ryoが目視で確認し、`verdict`（ok/ng/要修正）を決める。
5. 通ったものだけを `data/places.verified.json` に入れ、アプリに同梱する。
- 注意: スクリプトの Wikipedia REST API の項目名・挙動は**未確認**（この引き継ぎ書の作成時点で、Wikipediaへ接続できなかったため）。最初に1件だけ試し、必要なら修正する。
- 記事タイトルは推測なので、見つからない・曖昧さ回避のものはタイトルを直す。
- `User-Agent` の `OWNER/REPO` を実際のリポジトリURLに直す。
- 質が足りないカテゴリは、アプリの対象から外す。

## 7. 技術方針（提案。変えるなら理由を書く）
- 静的なWebアプリ（Vite + TypeScript、フレームワークなし、またはPreactなど軽量なもの）。GitHub Pagesで配信（HTTPS）。
- データは端末内（IndexedDB。写真は容量に注意）。サーバー・アカウントなし。
- 撮影: `<input type="file" accept="image/*" capture="environment">` を基本にする。独自カメラUIは後回し。
- アルバム画像: Canvasで描いてPNGにする。**フォントの読み込み完了を待ってから描く**。
- 共有: `navigator.canShare({files})` を確認してから `navigator.share`。ユーザー操作の中で呼ぶ。失敗時はダウンロードにフォールバック。
- PWA: manifest、ホーム画面に追加、オフライン時の最低限のキャッシュ。
- プライバシー: 位置情報と識別子の組み合わせや、蓄積から自宅・勤務先が推測できる情報は個人情報になりうる。端末内に留める方針を崩さない。

## 8. デザイン方針
- 参考にするのは「街にあるもの」。見た目の理由を一言で説明できないデザインは採用しない（「AIっぽい」と評価された見た目を避ける）。
- 最初に作る2枚:
  - **駅名標（駅・路線）**: 背景 #F1F1EE、文字 #1B1B1B、路線色の帯。フォント BIZ UDPGothic ＋ DM Mono。大きな駅名＋ひらがな＋ローマ字＋前後の駅。
  - **由緒書き（寺社）**: 背景 #D8D3C6、札 #FBF8EE、枠 #3B2A1E。名前は縦書き（BIZ UDPMincho）。理由は歴史／暦／好きの切り替え。
- アルバム: **往復きっぷ**。紙色 #F6EEDB、日付印の赤 #B3261E。
- 守ること: タッチ領域は44px以上、文字のコントラスト比は4.5:1以上、絵文字は使わない、文言は日本語で短く。
- 種類ごとに見た目が分かれるので、色・線の太さなど少数のルールで統一感を取る（未解決の課題）。

## 9. 最初の作業（この順で）
1. リポジトリを作る（名前はRyoに聞く。公開でよいが、写真・位置情報は絶対に含めない）。このファイルを分割して `CLAUDE.md` と `docs/SPEC.md` に保存。
2. 同梱ファイルを配置し、Pagesの設定を行う。Ryoがスマホで押す操作は最小限に。
3. データ整備（第6節）を回し、結果をスマホで読める形で出す。
4. 質が確認できたら、「行き先カード（駅名標と由緒書き）」を、検証済みデータから表示する。
5. お題 → 撮影 → ツイスト → 一言 → きっぷ画像の書き出し → 共有。ここまでを薄い一本道で通す。
6. 実機（iPhone）で確認するもの: 撮影の流れ、画像の書き出し、共有画面（ストーリーズ候補に出るか）。ここが一番の不確実性。
